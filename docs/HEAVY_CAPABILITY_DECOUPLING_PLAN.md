# Lumina 重型能力解耦与按需交付实施计划

## 文档目的

这份文档把 `torch`、`transformers`、`cv2`、`llvmlite`、`live2d` 等重型能力从主程序中解耦的方案收口成一份可执行的实施计划。目标不是简单“删库”或“缩包”，而是把当前混在主启动链里的重型能力拆成明确的能力边界、独立交付单元和统一运行时 contract，让主界面更快出现、安装包更小、发布链更稳、后续大重构不再反复打穿边界。

## 当前问题

当前项目已经修通了冻结后端二进制链路，主程序在非 Vite 模式下可以启动本地冻结 exe，安装包也可以正常生成。但更底层的问题仍然存在：主程序、后端 core、worker、前端静态资源和模型资源之间的边界仍然过于松散，导致以下几个后果。

- 主安装包仍然背着大量并非“主程序最小启动闭环”所必需的内容。
- Live2D、STT、声纹、视觉链路等重能力会影响首屏显示和启动耗时。
- 某些可选能力的失败会污染启动日志，甚至误导为主程序故障。
- 构建和发布仍然是“一包到底”的思路，导致任意一个重能力都会拖慢整体构建、安装和更新。
- 后续如果代码大改，发布链和运行链很容易再次被重依赖拖回主路径。

## 总目标

- 让 `core-runtime` 成为真正的轻核心，能够独立启动、独立健康检查、独立发布。
- 让 `live2d-assets`、`stt-runtime`、`voiceprint-runtime`、`vision-runtime` 等能力以独立包交付。
- 让主程序先显示界面，再按需检查和加载重能力。
- 让主程序只依赖统一 contract，不再依赖重库细节、目录细节和历史路径约定。
- 让更新过程支持“主程序更新”和“能力包更新”解耦，避免每次都重下全部重资产。
- 让未来架构重构只影响实现，不影响发布边界和运行边界。

## 非目标

- 不是先做一层长期兼容桥再慢慢迁移。
- 不是继续在主程序里堆更多 `if frozen`、`if exists`、`if dev`。
- 不是按 Python 包名字拆包，而忽略业务能力边界。
- 不是先改 UI 文案掩盖慢启动，而不处理真正的重依赖路径。
- 不是为了拆包引入过度工程化的服务发现、插件市场、远程编排系统。

## 实施原则

- 先按能力边界拆，再按代码路径落地。
- 先证明归属，再改构建和发布。
- 主程序只认 contract，不认重依赖内部实现。
- 缺失可选能力时必须优雅降级，不能把可选能力故障升级为主系统故障。
- 重构时一次迁移到位，不保留长期双轨兼容层。
- 任何阶段都要有明确退出条件和回滚条件。

## 目标架构

目标状态下，项目的运行时会分成五类单元。

| 单元 | 角色 | 是否主程序必需 | 典型内容 |
| --- | --- | --- | --- |
| `core-runtime` | 最小可运行核心 | 是 | Electron 主壳、基础后端、配置、路由、能力注册、worker 调度 |
| `live2d-assets` | 角色渲染资源包 | 否 | Live2D 模型、Cubism runtime、纹理、动作资源 |
| `stt-runtime` | 语音识别运行时 | 否 | STT worker、ONNX 运行时、STT 模型、配置 |
| `voiceprint-runtime` | 声纹识别运行时 | 否 | 声纹模型、声纹驱动、如仍需则包含 `torch` |
| `vision-runtime` | 视觉/推理运行时 | 否 | `cv2`、`transformers`、`llvmlite` 等对应链路依赖 |

主程序负责发现这些单元、检查它们的状态、按需启动或提示安装，但不再把这些单元默认打进最小主链。

## 统一 contract

### contract 的地位

后续所有能力包的安装、发现、版本校验、启动、健康检查都必须通过同一份 contract 完成。主程序不能直接拼某个旧路径，更不能直接假设某个库一定存在。

### 建议文件

建议新增统一清单文件，例如：

- `config/capability_packages.json`
- 或 `config/capability_packages.yaml`

### contract 字段

每个能力包至少包含这些字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 能力包唯一标识，例如 `core-runtime`、`stt-runtime` |
| `version` | 能力包版本 |
| `minHostVersion` | 主程序最低兼容版本 |
| `installDir` | 安装目录 |
| `type` | `runtime` 或 `asset` |
| `entryExecutable` | 可执行入口，资源包可为空 |
| `healthEndpoint` | 健康检查地址，资源包可为空 |
| `requiredFiles` | 判定安装完整性的关键文件 |
| `resourceDirs` | 资源目录列表 |
| `autoStart` | 是否允许主程序自动拉起 |
| `optional` | 是否为可选能力 |
| `platform` | 平台限制 |
| `arch` | 架构限制 |
| `displayName` | 面向用户的能力名 |
| `failureMode` | 缺失时的降级方式 |

### contract 规则

- 主程序和能力包必须双向校验版本。
- 资源包和运行时包都要能被统一识别。
- contract 需要支持“已安装但版本过旧”“文件缺失”“平台不匹配”“运行失败”这几类状态。
- 主程序只消费结构化状态，不消费拼出来的错误文案。

## 目录规划

建议统一能力包安装目录，避免继续分散在 `public/`、`dist_backend/`、用户数据目录和临时目录里。

建议目录结构如下：

```text
Lumina_Data/
  packages/
    core-runtime/
      manifest.json
      version.json
      runtime/
    live2d-assets/
      manifest.json
      version.json
      live2d/
      libs/
    stt-runtime/
      manifest.json
      version.json
      runtime/
      models/
    voiceprint-runtime/
      manifest.json
      version.json
      runtime/
      models/
    vision-runtime/
      manifest.json
      version.json
      runtime/
      models/
```

如果后续决定把部分能力仍然跟随安装包分发，也必须遵守这个目录规则，只是分发方式不同，不能恢复到散乱路径。

## Phase 0：盘点与归属证明

这一阶段不改发布物结构，先完成事实盘点，避免边拆边猜。

### 输出物

- 一份重依赖归属表。
- 一份“主程序最小闭环依赖”白名单。
- 一份“默认安装不应包含”删除名单。
- 一份启动阶段导入时机表。

### 必做事项

- 找出 `torch`、`transformers`、`cv2`、`llvmlite`、`live2d` 在当前代码中的真实导入点。
- 记录每个导入发生在 Electron 主进程、后端 core、worker 启动还是请求时。
- 记录每个重依赖属于哪个业务能力，而不是属于哪个 Python 文件。
- 识别当前哪些依赖只是“被某个 hook 顺手带入”，但实际默认链路并不用。
- 给出每个重依赖的结论：保留在主包、移入能力包、延迟导入、直接删除。

### 退出条件

- 每个重依赖都有明确归属。
- 不能再出现“可能属于 STT，也可能属于视觉”这种模糊判断。
- 主程序最小闭环清单已经冻结。

## Phase 1：建立统一能力包注册表

这一阶段的目标是先把“能力包判断逻辑”收口成单一来源。

### 设计动作

- 新增 `CapabilityPackageRegistry` 或等价服务。
- 把路径判断、版本判断、安装完整性判断、入口解析、健康检查目标解析全部放进 registry。
- 让 Electron 侧和后端 core 都通过 registry 读能力状态。
- 把散落的 `if frozen`、`if file exists`、`if VITE_DEV_SERVER_URL` 分支从业务路径中移出，只保留在极少数启动适配点。

### 主程序行为目标

- 启动时只读取能力状态。
- 对于缺失能力，只返回 `unavailable`，不直接抛异常。
- 对于可自动启动的能力，registry 提供统一的拉起信息。

### 退出条件

- 主程序里能力发现逻辑只剩一个入口。
- UI、Electron 主进程、后端 core 不再各自判断同一能力是否存在。

## Phase 2：拆出 `live2d-assets`

这是收益最大、风险最低的一步，优先处理。

### 目标

- Live2D 模型与 Cubism runtime 不再成为主界面首屏的硬前置。
- 未安装 Live2D 时主界面仍然可以立即显示。
- Live2D 缺失时不再报 runtime 错误，不再白屏等待。

### 实施动作

- 把 `public/live2d` 和浏览器侧 Cubism runtime 资源整理成 `live2d-assets`。
- 前端角色层改成先读能力状态，再决定是否初始化 Live2D 插件。
- Live2D 插件改成动态加载 Cubism runtime，而不是默认静态依赖。
- 未安装 `live2d-assets` 时，渲染层显示轻量占位，不显示大段说明文字。
- 角色选择器只把未安装角色标记为“可安装”，不误报失败。

### 风险点

- 角色资源路径与后端静态资源路径可能再次分裂。
- Cubism runtime 如果仍被主包静态引用，会导致拆包失败但表面看似可用。

### 退出条件

- 主界面无 Live2D 也能稳定显示。
- 缺少 `live2d-assets` 时不再出现 `Could not find Cubism runtime`。
- 角色资源已通过 contract 定位，而不是写死在 `public/live2d`。

## Phase 3：拆出 `voiceprint-runtime`

这是去掉 `torch` 默认负担的关键阶段。

### 目标

- 声纹能力不再属于默认启动关键路径。
- 如果 `torch` 仅由声纹带入，就把它从默认后端产物中彻底移出。

### 实施动作

- 把声纹驱动、模型、初始化逻辑、数据库读写边界整理成 `voiceprint-runtime`。
- STT worker 不再默认假设声纹总是存在。
- 主系统把声纹视为可选能力，而不是启动闭环必需能力。
- 只有用户真的启用声纹时，才安装并启动该运行时。
- 声纹数据库不可用时，统一走“空能力/空资料”降级，不再污染主错误路径。

### 风险点

- 声纹逻辑目前可能与 STT 音频过滤链耦合，需要先收口接口。
- 如果把声纹拆出后仍然要同步调用，就会重新把等待时间带回 STT 主链。

### 退出条件

- 默认安装且不开启声纹时，不再包含 `torch`。
- 声纹包缺失时，STT 可正常使用。

## Phase 4：拆出 `stt-runtime`

这一阶段处理语音识别的重型依赖和模型。

### 目标

- 主程序和 core-runtime 不再为 STT 模型加载等待。
- STT 能力独立安装、独立启动、独立升级。

### 实施动作

- 把 STT worker 可执行文件、模型目录、依赖、配置全部收成独立包。
- 主 core 通过 contract 发现并拉起 `stt-runtime`。
- STT 模型路径统一落在 `stt-runtime/models`。
- 首次进入语音功能时，如果未安装 STT，再触发安装或提示下载。
- UI 上将语音状态改成结构化状态，而不是“按钮点了直接报错”。

### 风险点

- 首次语音使用时的体验需要补充安装进度和失败恢复。
- STT 端口与主程序端口的发现逻辑必须统一，不能再在多处写死。

### 退出条件

- 主程序即使完全不装 STT，也能正常启动和工作。
- 装上 `stt-runtime` 后，语音功能可恢复，且只影响语音链。

## Phase 5：处理 `cv2 / transformers / llvmlite`

这一阶段必须按事实归属处理，不能先入为主。

### 目标

- 主包不再带视觉或可选推理重依赖。
- 明确哪些依赖应进入 `vision-runtime`，哪些可以直接删。

### 实施动作

- 查清 `cv2` 的真实调用路径，是视觉能力、媒体处理还是遗留依赖。
- 查清 `transformers` 是默认链路需要，还是仅特定插件需要。
- 查清 `llvmlite` 是 `numba` 间接带入还是生产链路真正需要。
- 对每个依赖给出结论：删、懒加载、移入 `vision-runtime`。
- 如果创建 `vision-runtime`，必须先定义清楚能力范围，不接受“把不确定的都先塞进去”。

### 退出条件

- 主包内不再默认携带与视觉推理无关的重依赖。
- 每个被保留的重依赖都有明确能力归属。

## Phase 6：安装器与更新链

### 目标

- 安装器不再把所有能力一股脑塞进主安装包。
- 更新链支持主程序和能力包分离更新。

### 实施动作

- 主安装包默认只带 `core-runtime` 和必要壳层。
- 提供 `精简安装`、`推荐安装`、`自定义安装` 三种模式。
- 为每个能力包生成独立 manifest、hash 和版本元数据。
- 更新时支持只更新主程序，不重下未变化能力包。
- 新增本地缓存目录，避免重复下载同一能力包。
- 支持“能力包修复安装”，处理损坏或部分缺失情况。

### 风险点

- 如果安装器没有把失败状态与主程序分离，会造成“可选包安装失败导致主程序安装失败”。
- 更新链如果没有版本兼容校验，主程序和能力包会错配。

### 退出条件

- 主程序和能力包能够独立分发。
- 安装器可在缺少可选能力包时仍完成主程序安装。

## Phase 7：启动体验与 UI 状态机

### 目标

- 用户先看到界面，再看到能力状态。
- 能力缺失、下载中、初始化中都用统一状态表达。

### 实施动作

- 定义统一能力状态：`ready`、`installing`、`starting`、`unavailable`、`failed`。
- 把 Live2D、STT、声纹、视觉入口都改为读取同一状态模型。
- 主窗口在最短路径下显示，不等重能力。
- 缺少可选能力时不直接打断主流程，只在用户真正触发该能力时给简洁提示。
- 安装与初始化进度要可见，长时间任务要允许取消或稍后处理。

### 退出条件

- 白屏问题从架构上消失，而不是靠延迟或遮罩掩盖。
- 能力缺失时用户看到的是明确动作，而不是技术栈错误。

## Phase 8：构建系统改造

### 目标

- 构建从“一次打完全部”改成“按能力构建，再组装发布物”。

### 实施动作

- 把当前统一打包脚本改成按能力产物输出。
- 每个能力包单独产出可执行文件、资源目录、manifest 和 hash。
- 主构建只负责组装，而不直接把所有依赖扫进同一产物。
- 在 CI 中拆开主包构建、能力包构建、组装构建。
- 对主包体积设置上限守卫，超出直接失败。

### 退出条件

- 可以单独重建某个能力包，而不重建全链。
- 主包体积和能力包体积都可单独观测。

## 数据迁移与升级策略

- 升级时先扫描旧目录中是否已有 Live2D、STT、声纹、视觉资源。
- 能复用的包直接登记到新 registry，不强制用户重下。
- 旧路径迁移完成后，删除旧兼容写入路径，不保留长期双写。
- 若旧版本中某能力没有独立包概念，则在第一次启动时完成一次性归档和登记。

## 验证矩阵

每个阶段结束都至少覆盖以下组合：

| 场景 | 预期结果 |
| --- | --- |
| 仅安装主包 | 主界面可显示，核心功能可用，不崩溃 |
| 主包 + `live2d-assets` | Live2D 正常显示，角色资源可访问 |
| 主包 + `stt-runtime` | 语音识别可用 |
| 主包 + `voiceprint-runtime` 且数据库不可用 | 主程序正常，声纹优雅降级 |
| 主包 + 全能力包 | 所有能力可协同运行 |
| 能力包丢失 | 仅该能力 unavailable，不影响主启动 |
| 能力包损坏 | 能给出修复路径，不让主程序闪退 |
| 主程序升级，能力包未升级 | 能检测错配并给出明确状态 |

## 指标基线

所有阶段都需要持续记录这些指标：

- 主窗口可见时间。
- 主后端 core 健康检查完成时间。
- STT worker 就绪时间。
- Live2D 可交互时间。
- 主安装包体积。
- 全量安装体积。
- 主程序二次启动时间。
- 更新后首次启动时间。

## 风险与应对

| 风险 | 说明 | 应对方式 |
| --- | --- | --- |
| 路径再次分裂 | 多处写死目录后边界再次失效 | 所有能力路径只允许 registry 解析 |
| 版本错配 | 主程序与能力包协议不一致 | 双向版本校验和结构化状态 |
| 首次使用等待变长 | 按需安装把等待推迟到使用时 | 补安装进度、缓存和重试机制 |
| 升级后用户误以为功能消失 | 功能改成可选包后默认不在本机 | 首次启动扫描旧资源并自动登记 |
| 构建链复杂化 | 拆包后 CI 和发布流程变长 | 把复杂度封装到能力构建脚本，不扩散到业务代码 |
| 后续重构再次打穿边界 | 新功能又把重依赖拉回主包 | 加主包体积守卫和依赖归属检查 |

## 回滚策略

- 任一阶段上线前都保留上一稳定发布物。
- registry 支持回退到“单主包模式”的只读兼容识别，但该逻辑只用于回滚，不作为长期维护路径。
- 主程序和能力包版本信息要足够明确，保证能识别“当前版本需要回滚哪个包”。
- 若某能力包独立化后出现严重问题，允许该能力临时禁用，但不允许拖垮主程序。

## 阶段里程碑

| 里程碑 | 内容 | 通过条件 |
| --- | --- | --- |
| M1 | 完成重依赖归属盘点 | 每个重依赖都有明确能力归属 |
| M2 | 完成统一 contract 与 registry | 主程序只通过单一入口读能力状态 |
| M3 | `live2d-assets` 独立 | 主界面无 Live2D 也可快速显示 |
| M4 | `voiceprint-runtime` 独立 | 默认安装不再带 `torch` |
| M5 | `stt-runtime` 独立 | 主启动不再等待 STT 模型链 |
| M6 | `vision-runtime` 或删除名单落地 | `cv2 / transformers / llvmlite` 归属收敛 |
| M7 | 安装器与更新链完成 | 主包与能力包独立分发 |

## 推荐执行顺序

建议按以下顺序推进，不并行打散：

1. 先做归属盘点。
2. 再做 registry 和 contract。
3. 先拆 `live2d-assets`。
4. 再拆 `voiceprint-runtime`，优先把 `torch` 从默认链移出。
5. 然后拆 `stt-runtime`。
6. 最后处理 `cv2 / transformers / llvmlite`，按事实归属删除或拆出 `vision-runtime`。
7. 等能力边界稳定后，再改安装器和更新链。

这个顺序的原因很简单：先拆前端资源包能最快改善白屏和主界面体验；随后拆声纹能最快减掉 `torch`；再拆 STT 能把主启动从语音链里解放出来。视觉链放到后面，是因为它通常不是当前用户首屏体验的第一瓶颈。

## 阶段退出总标准

只有同时满足以下条件，才算这个计划真正完成：

- 主程序已经变成独立的轻核心。
- Live2D、STT、声纹至少三个能力可以独立安装和独立缺失。
- 主界面可见时间和安装包体积都有量化改善。
- 可选能力缺失不再污染主启动闭环。
- 主程序和能力包之间已经通过统一 contract 耦合，而不是通过历史目录、隐式导入和兼容层耦合。
